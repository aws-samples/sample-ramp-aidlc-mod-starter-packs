# AIDLC v2 Gap Analysis for the RAMP Blueprint Repository

**Research date:** 2026-11-04
**Upstream evaluated:** `awslabs/aidlc-workflows` stable release `v2.11.2` (`10a9bc9`, released 2026-10-28), plus current official documentation on `main`
**Local repository:** `sample-ramp-aidlc-mod-starter-packs`

## Executive conclusion

The local repository should stop owning a separate, prose-driven copy of the AI-DLC lifecycle inside every starter pack.

AI-DLC v2 is now a real workflow platform:

- a deterministic orchestration engine owns routing and state transitions;
- a harness-neutral `core/` is projected into thin integrations for seven supported coding harnesses;
- typed stage files declare agents, inputs, outputs, dependencies, scopes, sensors, execution topology, and review policy;
- workflow profiles select an appropriate route and ceremony level;
- spaces, intents, persistent state, audit shards, knowledge, rules, and code knowledge bases support long-running and multi-team work;
- additive plugins extend core stages and add new stages without modifying upstream core;
- packaging, configuration, updates, diagnostics, ownership tracking, validation, and release provenance are productized.

The local repository currently reimplements only a small subset of that behavior using 14 independent `aidlc-workflow.md` files of 426–591 lines each. Every file has a different hash. Routing, gates, state, audit, and task sequencing live mainly in prose, and tool-specific output is generated by a local renderer. This creates permanent drift from upstream and drift between packs.

The recommended model is:

> **Upstream AI-DLC is the workflow kernel. RAMP is the modernization operating model. RAMP blueprints are composable product overlays.**

RAMP should pin a tested upstream release, install its native harness runtime, and add RAMP behavior through plugins, scopes, knowledge, rules, domain skills, MCP registrations, and golden templates. RAMP phases 1–4 must remain a program-level lifecycle above AI-DLC; they should not be renamed or forced into a one-to-one mapping with AI-DLC’s five software-delivery phases.

## What AIDLC v2 now provides

### 1. One core, many harnesses

Upstream authors methodology and engine behavior once under `core/`. Thin integrations live under `harness/<name>/`. Packaging projects that source into Claude Code, Kiro CLI, Kiro IDE, Codex CLI, Cursor, opencode, and GitHub Copilot.

Generated `dist/` and `dist-release/` trees are ignored and never hand-edited. Packaging builds them twice and byte-compares the results as a determinism guard.

This is materially more robust than maintaining independent transformations inside every RAMP pack.

### 2. Deterministic engine, thin conductor

The current upstream design explicitly replaced the old “prose orchestrator” model.

- The deterministic engine decides what happens next, resolves scope, reads state, routes stages, opens gates, handles resume/jump/skip, and commits transitions.
- The conductor executes the named stage well: it loads personas and knowledge, asks questions, produces artifacts, and surfaces judgment at gates.
- Engine-to-conductor communication uses validated typed directives.

This separation is important for RAMP. Program policy and modernization expertise can remain readable Markdown, while workflow progression, state integrity, and gate semantics should not depend on an LLM consistently interpreting hundreds of repeated prose lines.

### 3. Five phases and typed stages

Upstream currently describes five phases and 33 stages:

1. Initialization
2. Ideation
3. Inception
4. Construction
5. Operation

Each stage is one Markdown file with YAML frontmatter plus executable prose. The frontmatter can declare:

- phase and stage identity;
- lead and support agents;
- inline, subagent, pipeline, or mob topology;
- consumed and produced artifacts;
- dependency edges;
- per-unit execution;
- applicable scopes;
- reviewer and review policy;
- sensors;
- ceremony and conditional behavior.

The stage graph and scope grid are compiled from these authored files. This gives RAMP a much better extension point than whole-pack workflow forks.

### 4. Adaptive workflow profiles

AI-DLC does not run every request through identical ceremony. Its user-facing profiles—called scopes by the engine—include:

- Classic
- Express
- Feature
- Enterprise
- MVP
- Proof of Concept
- Bugfix
- Refactor
- Infrastructure
- Security Patch
- Workshop

Profiles select stage membership, depth, test strategy, review ceiling, and ceremony defaults. Rich or ambiguous work can use an adaptive composer to propose a tailored plan.

This is a key correction for the local repository. “QA automation,” “vulnerability remediation,” “infrastructure,” “MVP workshop,” and “enterprise modernization” are not all the same kind of category. Some are workflow profiles, some are domain accelerators, some are modernization journeys, and some are solution patterns.

### 5. Durable spaces, intents, state, and audit

Upstream stores shared runtime-neutral information under:

```text
aidlc/
└── spaces/<space>/
    ├── memory/
    ├── knowledge/
    ├── codekb/<repo>/
    └── intents/
        ├── intents.json
        └── <YYMMDD>-<label>/
            ├── aidlc-state.md
            ├── audit/<host>-<clone>.md
            └── <phase>/<stage>/*
```

This supports multiple pieces of work, multiple repositories, team-shared context, and concurrent clones without a single append-only audit file becoming a merge hotspot.

The local flat `aidlc-docs/` pattern was useful as an early implementation but is now a compatibility island. New RAMP designs should use the upstream state model rather than add more behavior to the old layout.

### 6. Knowledge and rules are separate concerns

AI-DLC v2 distinguishes:

- framework methodology knowledge, shipped and upgraded with AI-DLC;
- team knowledge, stored by the adopting team;
- behavioral rules, resolved through org/team/project/phase/stage layers;
- per-intent artifacts, generated by workflow stages;
- shared per-repository reverse-engineering evidence in `codekb`.

This directly answers where many RAMP cross-cutting assets should live:

- explanatory AWS patterns and trade-offs: knowledge or skills;
- mandatory security/governance behavior: rules;
- a golden infrastructure implementation: template;
- a repeatable lifecycle extension: plugin stage or contribution;
- customer-specific facts: customer-owned knowledge or overlay;
- findings for one workload: intent artifact or code knowledge base.

They should not all be merged into an `aidlc-workflow.md`.

### 7. Additive plugin model

The official `test-pro` plugin demonstrates the intended extension seam.

A plugin can:

- add new stages;
- add outputs, inputs, sensors, dependencies, required sections, and prose fragments to existing stages;
- add personas;
- add scopes;
- ship tools and diagnostics;
- validate and test its own content.

Core-stage contributions are additive: plugins can add but cannot override or remove core behavior. Artifacts are namespaced to prevent collisions. Composition is idempotent.

This is the strongest available mechanism for a RAMP integration that remains upgradeable.

### 8. Productized install, lifecycle, and ownership

The stable release provides:

- native installers;
- `aidlc config --harness ...`;
- `aidlc doctor`;
- stable/preview channels;
- updates and project refresh;
- version pinning;
- offline/manual-copy distribution;
- checksums, attestations, and release provenance;
- project ownership manifests that distinguish framework-owned files from project-owned files;
- transactional changes and rollback behavior.

The local installer is a useful prototype, but reproducing these lifecycle features would consume effort that should instead go into RAMP-specific modernization value.

### 9. Layered validation

Upstream tests:

- source and structural contracts;
- individual tools and schemas;
- cross-component routing and state behavior;
- full lifecycle and rendered-terminal journeys;
- packaging determinism;
- release/update paths across operating systems and harnesses.

The local repository tests rendering and selected pack contracts, but it does not provide comparable behavioral assurance for each prose workflow.

## Local-to-upstream gap matrix

| Concern | Local repository today | Current upstream model | Recommendation |
|---|---|---|---|
| Workflow core | One long prose workflow per pack | Deterministic engine + typed stages + thin conductor | Replace local core with pinned upstream |
| Adaptiveness | Pack chosen before installation; pack prose fixes route | Profiles/scopes + adaptive composer + overrides | Use upstream profiles; add only RAMP-specific scopes where justified |
| State | Mostly flat `aidlc-docs/aidlc-state.md` | Spaces, intents, per-intent state, shared code KB | Migrate to upstream workspace model |
| Audit | Pack-specific append-only audit conventions | Typed event taxonomy and per-clone audit shards | Adopt upstream audit; add RAMP outcome events outside core if needed |
| Approvals | Repeated prose rules | Engine-owned gates and receipts | Adopt directly |
| Stages | Hard-coded sections inside each workflow | File-authored, typed, compiled stage definitions | Express RAMP extensions as stages/contributions |
| Agents | Mostly provided indirectly through skills/tool behavior | 14 personas and declared stage topologies | Reuse personas; add only clear modernization-specific roles |
| Cross-cutting guidance | Mixed across workflow, skill activation, README, and skills | Knowledge, rules, skills, sensors, templates, plugins | Route each asset by responsibility |
| Tool support | Local renderer for Kiro, Claude, Copilot, Cursor | Native runtime for seven harnesses | Let upstream own harness adaptation |
| Distribution | Copy scaffolds or run local Node installer | Native installer/config/update/doctor and manual copy | Wrap upstream config; do not recreate it |
| Generated files | Tool-specific scaffolds committed under every pack | Generated projections ignored | Stop committing per-pack harness projections after migration |
| Ownership/drift | README warns not to hand-edit generated files | Ownership manifest, hashes, refresh conflicts, transaction engine | Adopt upstream lifecycle |
| Validation | Installer unit tests and selected content tests | Smoke, unit, integration, E2E, determinism, release acceptance | Add RAMP plugin/catalog tests on top of upstream |
| Upstream sync | Attribution link but no version or compatibility contract | Stable releases and project pins | Add explicit upstream lock and compatibility CI |
| Catalog metadata | `name`, `title`, description, instructions, MCPs, skills | Scopes/stages/plugins are typed but not a RAMP catalog | Create a richer RAMP blueprint schema |

## Adopt, wrap, extend, and avoid

### Adopt directly

RAMP should consume these as upstream-owned capabilities:

- the deterministic orchestration engine and typed directive contract;
- the five-phase/33-stage lifecycle;
- state transitions and approval gates;
- spaces, intents, state, audit, code knowledge base, and runtime graph;
- stock profiles/scopes and adaptive composition;
- existing agent personas and stage execution topologies;
- stage, artifact, rule, sensor, knowledge, and plugin contracts;
- native install, config, update, pin, doctor, and project ownership behavior;
- harness packaging and supported harness projections;
- upstream test and release-provenance model.

These should not be copied into RAMP source.

### Wrap with RAMP experience

RAMP should provide a thin user experience above upstream:

- a `ramp init` or equivalent guided selector;
- RAMP lifecycle language and phase handoffs;
- blueprint discovery based on modernization intent and estate characteristics;
- preflight for AWS Transform, source/FSD availability, target environment, and customer constraints;
- RAMP Phase 1 workshop setup using the upstream `workshop`, `mvp`, `poc`, or composed profile;
- RAMP Phase 2 production and executive-readout evidence;
- RAMP Phase 3 portfolio assessment and wave-plan orchestration;
- RAMP Phase 4 platform adoption and change-management playbooks;
- outcome capture: speed, deployed scope, quality, production readiness, business value, and executive decision.

The wrapper should call upstream commands and read upstream state rather than emulate them.

### Extend through plugins and composable assets

Candidate first-party RAMP extensions include:

1. **`ramp-modernization` plugin**
   - stronger brownfield scope and evidence contracts;
   - AWS Transform/ATX and third-party assessment ingestion;
   - modernization strategy and target-state decision surfaces;
   - behavior-parity, migration, cutover, and rollback artifacts;
   - before/after architecture and modernization outcome evidence.

2. **`ramp-production-readiness` plugin**
   - RAMP Phase 2 hardening;
   - production-readiness assessment;
   - operational acceptance;
   - executive-readout evidence and outcome pack.

3. **`ramp-portfolio` product**
   - estate intake and portfolio normalization;
   - workload scoring and dependency graph;
   - wave planning;
   - blueprint recommendation per workload;
   - parallel platform-foundation work.

   This may be a separate orchestration application or program workflow rather than a normal per-repository AI-DLC plugin. Do not force portfolio management into a single software intent.

4. **Blueprint-specific extension modules**
   - legacy decomposition;
   - framework/runtime upgrade;
   - COTS/low-code reimagination;
   - API platform exit;
   - database modernization;
   - agentic-readiness modernization.

5. **Cross-cutting accelerators**
   - regression safety net;
   - automated QA;
   - vulnerability remediation;
   - IaC generation and verification;
   - CI/CD and release engineering;
   - observability and incident response.

These should compose with journeys rather than compete with them as sibling “use cases.”

### Deliberately avoid

Do not:

- fork upstream core unless a required capability cannot be implemented through a documented extension seam;
- copy upstream stage or protocol prose into every RAMP blueprint;
- edit upstream Tier 1 framework knowledge or generated harness files;
- commit generated harness projections for every blueprint;
- recreate native install/update/doctor/pinning in the RAMP installer;
- treat a domain skill as a workflow stage, or a workflow profile as a business use case;
- assume the plugin `when:` predicate is active—official documentation states that its current accepted schema is not yet evaluated;
- assume advisory sensors are blocking policy controls;
- track `main` for customer delivery;
- put customer-specific evidence or proprietary patterns into the public canonical catalog;
- equate RAMP Phase 1–4 with AI-DLC Initialization–Operation phases.

## Version and upstream-sync strategy

### Recommendation: pinned upstream dependency plus additive RAMP extensions

Use stable releases, not the upstream `main` branch.

Maintain:

```text
upstream/
├── aidlc.lock.yaml
├── compatibility.yaml
├── patches/                 # normally empty
└── sync-notes/
```

Example lock:

```yaml
source: awslabs/aidlc-workflows
channel: stable
version: 2.11.2
commit: 10a9bc9
verifiedAt: 2026-11-04
```

Rules:

1. Customer-facing releases use an exact upstream version.
2. One compatibility matrix records tested RAMP plugin/blueprint versions for each AI-DLC version.
3. Upgrades happen in a dedicated branch on a fixed cadence or for a critical fix.
4. CI installs the candidate upstream release and runs representative RAMP journeys on every supported harness tier.
5. Breaking upstream changes are handled in the RAMP extension layer.
6. Any core patch must have:
   - a written reason the extension seams were insufficient;
   - a minimal patch file;
   - an upstream issue/PR when appropriate;
   - an expiry/removal condition.
7. Release notes state both RAMP catalog version and AI-DLC runtime version.

### Why not a Git submodule?

A submodule makes source browsing easy but does not itself solve runtime installation, cross-platform packaging, update safety, or customer project ownership. Upstream already provides native releases and version pinning. Prefer consuming the release contract; use a development checkout only for extension validation.

### Why not a long-lived fork?

A fork would make RAMP responsible for thousands of workflow-engine, harness, lifecycle, concurrency, and release fixes. The upstream v2.11.x release history demonstrates a high change rate across gates, hooks, session routing, multi-repository work, worktrees, config refresh, and cross-platform behavior. RAMP’s differentiation is modernization, not maintaining an AI coding harness.

## Migration plan

### Stage 0 — Freeze and characterize

- Stop creating new pack-local core workflow variants.
- Inventory each current workflow section as one of:
  - upstream core behavior;
  - RAMP program behavior;
  - modernization extension;
  - blueprint-specific domain behavior;
  - cross-cutting accelerator;
  - customer-specific content;
  - obsolete duplication.
- Record current golden behaviors as regression scenarios before deleting prose.

### Stage 1 — Prove composition with two representative blueprints

Use two deliberately different pilots:

1. `legacy-transformation-on-aws`
   - brownfield;
   - deep reverse engineering;
   - modernization decisions;
   - broad AWS target options.

2. `vulnerability-remediation-pipeline`
   - focused security/delivery automation;
   - demonstrates that an accelerator is not a modernization journey;
   - exercises a short upstream scope such as security-patch plus domain plugins/skills.

For each pilot:

- configure upstream stable AI-DLC;
- reproduce the essential user outcome using stock scopes plus minimal RAMP plugin contributions;
- compare artifacts, gates, resume behavior, installation size, and maintenance surface;
- retain no duplicate upstream stage prose in the blueprint.

### Stage 2 — Build the RAMP extension SDK

- Define the blueprint manifest schema.
- Create `ramp-modernization` plugin.
- Establish namespaced artifacts and validation.
- Define the boundary between plugin, skill, knowledge, rule, template, and MCP.
- Add an upstream compatibility harness.
- Add a catalog linter and generated documentation.

### Stage 3 — Reclassify and migrate assets

Migrate content into:

- modernization journeys;
- workload patterns;
- delivery accelerators;
- platform foundations;
- domain skills;
- golden templates;
- RAMP program playbooks.

Retire `agentic-ai-workflow` as a user-facing pack. Its responsibility becomes the pinned upstream runtime plus the RAMP base plugin/profile.

### Stage 4 — Replace local harness generation

- Make upstream `aidlc config` the harness installer.
- Change the RAMP installer into a composition tool.
- Stop committing `scaffolded-packs/` after the new distribution path is proven.
- Keep a temporary legacy export command only for existing workshop users who cannot upgrade immediately.

### Stage 5 — Migrate users safely

- Publish a mapping from old pack names to new composition recipes.
- Detect existing `aidlc-docs/` projects and leave them resumable under the legacy version.
- Start new work on the v2 runtime.
- Avoid in-place conversion of active engagements unless a tested migration exists.
- Set an explicit end-of-support date for legacy pack-local workflows.

## Compatibility risks and mitigations

### RAMP phases versus AI-DLC phases

**Risk:** Users confuse the four program phases with the five delivery phases.
**Mitigation:** Use distinct labels consistently: “RAMP Program Phase” and “AI-DLC Delivery Phase.” Add a mapping table showing that a RAMP phase can contain one or several AI-DLC intents.

### Plugin capability limits

**Risk:** A design depends on declared but not yet enforced features such as `when:` or blocking sensors.
**Mitigation:** Design to the stable implemented contract; validate scope gating explicitly; use deterministic RAMP tooling for hard policy.

### Fast upstream evolution

**Risk:** New releases change project layouts, harness surfaces, or extension contracts.
**Mitigation:** Pin stable versions, maintain compatibility tests, and upgrade intentionally.

### Existing workshop continuity

**Risk:** Current projects rely on `aidlc-docs/` and current commands.
**Mitigation:** Version the legacy packs, do not silently rewrite active projects, and provide a parallel v2 start path.

### Skill namespace and quality

**Risk:** The local skills library contains heterogeneous provenance, metadata, maturity, and overlapping responsibilities.
**Mitigation:** Add skill ownership, version, source, license, maturity, compatibility, and quality gates. Treat upstream AI-DLC agents/knowledge separately from RAMP domain skills.

### Generated-file ownership

**Risk:** RAMP composition overwrites project or upstream-managed files.
**Mitigation:** Use upstream’s project ownership/transaction model where possible; require all additional RAMP writes to have the same explicit ownership and rollback discipline.

### Public versus customer-specific assets

**Risk:** Customer patterns or evidence leak into the public canonical catalog.
**Mitigation:** Define customer overlays as separate repositories or local packages. The public blueprint references extension interfaces, never customer data.

### Portfolio orchestration mismatch

**Risk:** RAMP Phase 3 estate planning is forced into a single code repository workflow.
**Mitigation:** Model a portfolio as a program with many workload intents and repositories. Use upstream multi-repository capabilities within a workload where appropriate, not as a substitute for portfolio management.

## Decision recommendations

1. **Adopt AI-DLC v2 as a pinned dependency, not copied content.**
2. **Use plugins as the default workflow extension seam.**
3. **Retain RAMP as a program layer above AI-DLC.**
4. **Make the catalog multi-dimensional and manifest-driven.**
5. **Turn the local installer into a composer of upstream runtime plus RAMP assets.**
6. **Pilot on one modernization journey and one accelerator before bulk migration.**
7. **Keep existing engagements on a versioned legacy path until complete.**
8. **Do not commit new generated per-harness scaffolds.**
9. **Add explicit upstream version, compatibility, maturity, ownership, provenance, and test metadata.**
10. **Invest engineering capacity in modernization intelligence, portfolio wave planning, productionization, and platform foundations—not in another AI-DLC engine.**

## Validation questions for the RAMP owner

These do not block the architectural recommendation, but they affect sequencing:

1. Is the colleague’s customer attempt one of the Adi-authored vulnerability-remediation, framework-upgrade, or incident-response packs? Those are useful migration pilots because git history preserves their pre-generalization shape.
2. Must workshops work fully offline or in environments where the native upstream installer is prohibited?
3. Which harnesses are contractually required for FY27: all upstream-supported tools, or a certified subset?
4. Will the public repository hold only generalized assets while customer overlays live privately?
5. Should RAMP Phase 3 portfolio planning be built in this repository, or owned as a separate program-level product that consumes the blueprint catalog?
6. Is backward compatibility with current `ramp-pack` commands required, and for how long?
